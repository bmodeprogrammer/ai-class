Part 1 of 4 Form your team Introduce yourselves, agree how to work and make room for everyone.

Start with the team size assigned by the facilitator; the current workshop plan is teams of four. Share your experience with frontend, backend, data and AI coding tools.

Agree who drives the keyboard, who reviews the agent's output and how you will validate results. Rotate responsibilities: nobody should spend the whole exercise only watching.

Ready when: everyone knows the team, how to participate and who owns the next action.

Part 2 of 4 Share a repository Create one team starting point, then give everyone access.
  1. Choose a repository owner. Create one GitHub repository for the team, private if required by the facilitator.
  2. Extract the supplied bootstrap ZIP. Put the contents of the extracted bootstrap folder at the repository root, so the root contains the apps, docs and CLAUDE.md files and folders.
  3. Before the first commit, confirm the supplied ignore rules are present. Do not upload installed dependencies, build output, local settings (which hold your API key) or datasets.
  4. Push the starter, invite every teammate and have everyone clone it. Open the cloned repository root in VS Code, not just the frontend subfolder.

The bootstrap is a single repository with a folder for each application: apps/web for Next.js and apps/api for NestJS. Specifications go in docs.

Ready when: everyone can work from the same starting commit. Keep changes small and review them before merging.

Part 3 of 4 Prepare your workspace Install the tools and connect Claude Code to the workshop API.

Install the essentials

  • VS Code (latest), for the editor and integrated terminal.
  • Git (latest), for version control and the team repository.
  • Node.js (includes npm), version 24 LTS or newer.
  • Claude Code CLI (latest), the AI coding agent used in the VS Code terminal.

Confirm that the tools are available

node --version
npm --version
git --version
claude --version

All four commands must print a version. Node must be 24 or newer.

Install Matt Pocock's skills

Install the official Matt Pocock skills Claude Code plugin:

claude plugin install mattpocock-skills@claude-plugins-official

The plugin updates itself. See the official skills repository for details.

Connect Claude Code to the workshop API

Deloitte provides the workshop API URL and key. Use only the values assigned by the facilitators; you do not need a personal API key, billing setup or Claude subscription.

From the repository root, in .claude/settings.local.json, set both ANTHROPIC_FOUNDRY_BASE_URL and ANTHROPIC_FOUNDRY_API_KEY under env, using the URL and key provided by Deloitte. If you need to create the file, use this structure and replace the empty values:

{
  "env": {
    "ANTHROPIC_FOUNDRY_BASE_URL": "",
    "ANTHROPIC_FOUNDRY_API_KEY": "",
    "ANTHROPIC_MODEL": "claude-sonnet-5-5",
    "ANTHROPIC_DEFAULT_SONNET_MODEL": "claude-sonnet-5-5",
    "ANTHROPIC_DEFAULT_HAIKU_MODEL": "claude-haiku-5-5",
    "DISABLE_NON_ESSENTIAL_MODEL_CALLS": "1",
    "CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC": "1",
    "CLAUDE_CODE_USE_FOUNDRY": "1"
  }
}

If env already exists, add or update the entries there. Never put the URL or key in .claude/settings.json; keep both only in .claude/settings.local.json, which is excluded from Git. Start Claude Code from the repository root:

claude

Run /status to confirm it is connected, then run /setup-matt-pocock-skills once to configure the skills for this repo.

Keep the URL and key private. Put the URL and key only in .claude/settings.local.json, which is excluded from Git. A Claude hook blocks commits with non-placeholder values for either variable in staged files. Never commit or share either value or put either value in application code. Report a leaked key immediately to the Deloitte facilitators. If the key is rejected or its usage limit is reached, contact them; do not use a personal key.

Part 4 of 4 Understand the challenge Choose one business domain and turn the brief into an agreed specification.

Read one of the assignment PDFs supplied separately with the workshop materials. The brief is your source of requirements. The starter and this guide do not replace it.

E-commerceExplore marketplace operations, delivery and logistics indicators.
Hospital supplyExplore stock and replenishment for logistics decisions, not clinical decisions.
Footwear warehouseExplore order profiles, waves and product-sector distribution.

Follow this workflow

Your team works through the stages below in order. Humans own the what and the final decision; the agent does most of the how.

Think — human-led, agent-assisted

  1. initial promptWrite and refine it
  2. grill-with-docsAlign on what
  3. to-specWrite it down
  4. to-ticketsSlice it

Build & verify — agent-led, human-gated

  1. implementTDD per ticket
  2. code-reviewFresh eyes
  3. human verifyYou decide
Ship ✓ when verified Bug found → triage (diagnose → regression test) → new ticket → back to implement

improve-codebase-architecture — periodic; feeds new tickets.

Guardrails at every step: hooks · lint · types · tests · Sonar · CI

Step 1 — create and refine the initial prompt. Draft a first prompt from the chosen brief and iterate on it until it states the goal, context, constraints and expected output clearly.

Agree what to build before building it

  1. User and decisions: identify the primary user and at least three business questions. What concrete decision will each answer support?
  2. Data and indicators: inspect the CSV structure; specify formulas, units, date fields, exclusions, ABC criteria where applicable and how to handle missing or ambiguous data.
  3. Interactions: specify consistent dynamic filters, time comparisons, and the required tooltip, drill-down and drill-through examples.
  4. Acceptance: define expected calculations and automated test cases for the minimum indicators. State limitations instead of inventing facts or silently approximating.

Save the agreed specification in the initially empty docs folder. Put the chosen original CSV files in data; keep them unchanged and out of Git. Decide on the ORM, chart library and internal modules from the specification, not before it.

Architecture boundary: browser → Next.js → NestJS → data store. Data access, indicators and filters are server-side. Implement a reproducible CSV ETL; never have the browser read the dataset or connect directly to the data store.

Then select one small end-to-end slice, implement it with tests, review the changes and independently validate a calculation against a small known example.

Intentionally not supplied: database models, ORM, ETL, indicators, dashboards or domain tests. Building them is the exercise.
